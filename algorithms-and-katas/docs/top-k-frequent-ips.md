# 10GB IP 文件 + 100MB 内存：找出现次数最多的 10 个 IP

> 本文探讨「数据装不进内存」时的哈希分片计数方案：为什么分片内计数等于全局计数、各片 Top-10 的并集为什么覆盖全局 Top-10（附证明）、内存预算怎么算、P 取多少，以及 IPv6、流式、阈值型、去重计数等变体的处理方式。

## 问题与约束

- 输入：10GB 的 IPv4 地址文件，每行一个 IP（`a.b.c.d`）。
- 内存：整机 100MB。
- 输出：出现次数最多的 10 个 IP 及其次数。

先做数量级估算：

| 量 | 估算 |
| --- | --- |
| 行数 | 10GB ≈ 10^10 B ÷ 约 10 B/行 ≈ **10^9 行** |
| 唯一 IP 上界 | min(2^32, 行数) ≈ 最多 10^9 |
| 全量频次表（最坏全唯一，编译型 ~20B/条） | ~20GB ≫ 100MB |

结论：一趟全量哈希表装不下，必须把问题切成「每块都装得进 100MB」的小问题。

## 可利用的两个性质

1. **一致性分片**：同一个 IP 经过确定性哈希一定落进同一个分片，所以该 IP 的所有出现都在同一片里——**分片内计数就是全局计数，不需要跨片合并计数**。这是本题最核心的一点。
2. **域有限可压缩**：IPv4 只有 2^32 个取值，IP 可无损压成 uint32；计数用 uint32 也够（行数 < 2^32）。

## 方案对比

| 方案 | 思路 | 峰值内存 | 总 IO | 评价 |
| --- | --- | --- | --- | --- |
| **A. 哈希分片两遍（推荐）** | 按 hash(ip) % P 把文件切成 P 片；逐片内存计数 + 本地 Top-10；最后合并 | O(行数/P) | ~30GB | 精确、O(N)、实现简单 |
| B. 外部排序 | sort 生成有序 run → 归并 → uniq -c → Top-10 | 排序缓冲 + 10 元堆 | 60–70GB | 能跑通，但每元素多一次比较、IO 多一倍；本题不需要排序 |
| C. 域分片 + 位图 | 2^32 位图 = 512MB 直接放不下；切 8 段各 2^30（位图 64MB），多遍扫描标记存在 | 64MB 位图 | ≥8 遍 | 对「出现 ≥ K 次」阈值型变体有用；对 Top-10 不如 A |
| D. 采样 + 精确复核 | 采样出候选 → 全量扫一遍只数这 10 个（10 个计数器） | O(1)（复核阶段） | ~15GB | 快；但「采样里没出现的 IP 一定不在 Top-10」不严格成立，属近似解，只适合重频 |

D 的采样比例由内存决定：~100MB ÷ 20B/条 ≈ 5×10^6 条 ≈ 0.5% 数据。全局计数 c 的 IP 在样本里期望出现 c/200 次，只有 c 达数百以上才稳——所以采样法只适合找「明显的高频 IP」。

## 推荐方案细节（A：两遍分片 + Top-10 合并）
```mermaid
flowchart LR
    A["10GB ips.txt<br/>约 10^9 行"] -->|"第1遍<br/>hash(ip) % P 写分片"| B["shard_0 … shard_(P-1)<br/>P 个分片文件"]
    B -->|"第2遍<br/>每片内存计数 + 10元小顶堆"| C["各分片本地 Top-10<br/>候选 ≤ 10×P 条"]
    C -->|"第3遍<br/>合并候选并排序"| D["全局 Top-10"]
```


三趟：

1. **分片**：顺序读原文件，IP → uint32 v，h = mix(v) % P（mix 把高位混进低位，见下），行追加到 `shard_h`。
2. **逐片计数**：每片独立处理，片内建 uint32→uint32 计数表（片内唯一数 ≈ 10^9/P），同时维护 10 元小顶堆只留本片 Top-10，释放后处理下一片。
3. **合并**：候选 ≤ 10×P 条（P=1024 时 1 万条以内），内存排序取前 10。

**为什么各片 Top-10 的并集 ⊇ 全局 Top-10**：
设 IP x 全局排名 r ≤ 10，落在片 s。由性质 1，x 的全局次数 c(x) 等于片 s 内次数。若 x 不在片 s 的 Top-10，则片 s 内有 10 个 IP 按 (次数, 平局规则) 严格优于 x；这些 IP 的全局次数同样等于其片内次数，故全局排名全部高于 x，r ≥ 11，矛盾。∎

**内存预算**（行数 ≈ 10^9、均匀分布，片内唯一数 ≈ 10^9/P）：

| P | 片文本 | 片内唯一数 | 编译型 Go/C（~20B/条） | 解释型 awk/Python（~100B/条） |
| --- | --- | --- | --- | --- |
| 128 | 80MB | 7.8M | 156MB ✗ | 750MB ✗ |
| 256 | 40MB | 3.9M | 78MB 临界 | 375MB ✗ |
| 512 | 20MB | 2.0M | 39MB ✓ | 190MB ✗ |
| 1024 | 10MB | 1.0M | 20MB ✓ | 95MB 临界 ✗ |
| 2048 | 5MB | 0.5M | 10MB ✓ | 47MB ✓ |

结论：**编译型（Go/C/Rust）取 P = 512~1024；解释型（awk/Python）取 P = 2048**。

**hash 取法**：别偷懒用 `v % P`——P 为 2 的幂时只看低 log2(P) 位，若数据集中在同一网段，大量 IP 会被挤进少数片。一行混合：Go 里 `v ^= v >> 9` 再取模，gawk 里 `xor(v, rshift(v, 9))`；也可直接用 32 位混合哈希（如 FNV-1a）。

**复杂度与代价**：

- 时间 O(N)：每行一次解析 + 一次哈希 + 一次计数，全 O(1)。
- IO ~30GB：第一遍 10GB 读 + 10GB 写，第二遍 10GB 读。HDD（100MB/s）约 5 分钟，SSD 1 分钟内。
- 磁盘：分片文件共 10GB，需 20GB 可用空间（原文件 + 分片）。
- 附带好处：分片把「排序」也变成了内存排序——每片去重后输出 ≤ 50 万行（~13MB），第二遍排序不需要外部归并。

**实现**：

gawk 一行版（P=2048）：

```bash
# 第一遍：分片（xor/rshift 是 gawk 扩展；2048 个文件 = 2048 个 fd，需 ulimit -n 4096）
awk '{ split($0, a, "."); v = (((a[1]*256)+a[2])*256+a[3])*256+a[4]
       print > ("shard_" (xor(v, rshift(v, 9)) % 2048)) }' ips.txt

# 第二遍：逐片计数，只留本地 Top-10
for i in $(seq 0 2047); do
  awk '{ c[$0]++ } END { for (ip in c) print c[ip] "\t" ip }' "shard_$i" \
    | sort -rn | head -10 >> top
done

# 第三遍：全局 Top-10（平局按 IP 段数值比较，-V 为 GNU 版本排序）
sort -k1,1nr -k2,2V top | head -10
```

注意：gawk 每条约 100B，P=2048 时片内计数表上限 ~50 万条 ≈ 50MB，加解释器后整机 100MB 可行；嫌 fd 麻烦就降回 P=1024 并换编译型实现。

Go 骨架：

```go
// 第一遍：P 个 *os.File + 每片一个小 buffer
v := ipToUint32(line)      // "a.b.c.d" -> a<<24|b<<16|c<<8|d
h := (v ^ (v >> 9)) % P    // 混合高位
bufs[h].WriteString(line)

// 第二遍：map[uint32]uint32 计数 + container/heap 的 10 元小顶堆
// 第三遍：10*P 个候选排序取前 10
```

**工程细节**：

- **格式假设**：每行一个 IP、无 CRLF/空格。不确定时先 `head` 看一眼，归一化后再分片与计数，两处哈希必须用同一个归一化值。
- **JVM 语境**：整机 100MB 跑 JVM，JVM 自身吃 50~80MB，`HashMap<String,Integer>` 每条约 130B 直接不可用；换 fastutil 的 `Int2IntOpenHashMap`（~8B/条），P=2048 时数据面 ~4MB 勉强能跑，但更稳的是 Go/C。
- **平局**：次数相同时建议明确「按 IP 数值升序」；证明用 (count, ip) 字典序避免歧义。
- **原文件只读 / 远端（NFS、对象存储）**：方案不变，第一遍需要 10GB 本地暂存；对象存储可用 range-get 按片读，省一次完整下载。
- **为什么不直接起 MapReduce**：10GB 单机绰绰有余；若规模升到 1TB，分片方案天然水平扩展——P 片分给 P 台机器各算本地 Top-10 再合并，代码与单机同构。

## 变体与延伸

- **对抗性分布：大量 IP 哈希进同一片？** 分片前统计各片大小，超预算的片换哈希做二级分片（再切 4 片）递归；总数据量有界，必然收敛。实际上第一遍取较大的 P 并观察分布即可，很少真触发。
- **只允许遍历文件一遍（流式）？** 精确解需要第二次计数；纯流式下退概率结构：Count-Min Sketch 估频次 + Space-Saving 保 Heavy Hitters，给出误差界。若允许「第二遍发生在磁盘上」，先流式落分片文件，本质还是两遍。
- **IPv6？** 域变 2^128：「压成 uint32」和位图方案都失效，条目变 ~40B/条，分片方案不变但 P 翻倍（编译型 ~4096）。
- **变体：找出现 ≥ K 次的 IP？** 分片精确统计后过滤（通用）；K 很大时可先采样/位图收缩候选集再精确复核，内存更省。
- **变体：统计去重后 IP 总数？** HyperLogLog：2^14 个寄存器 = 16KB，误差 ~0.8%——内存约束下的 distinct count 是 HLL 的招牌场景。
- **为什么不用布隆过滤器？** 布隆只回答「可能存在」，有假阳性、给不了计数，更没有排名；本题要的是精确 Top-10，用不上。
